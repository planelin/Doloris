指数退避

失败后立刻重试是最自然的反应，也是把一次小故障放大成雪崩的最快方式。指数退避回答的只有一件事：等多久再试，并把这个决定从本能变成可控参数。

机制要点

退避必须有上限和次数上限。没有 cap 的指数增长会让等待时间奔向无穷，把"重试"变成"无限期挂起"；没有次数上限则永远不进入终态，任务既不成功也不失败。

抖动不是可选装饰。多个 worker 若共享同一条退避序列，重试会被对齐到同一秒，等于亲手制造尖峰。sleep = min(base × 2ⁿ, cap) × (0.5 + rand × 0.5) 让重试在时间上摊开。

服务端给了 retry-after 就优先服从它，本地序列只作为兜底。用本地猜测覆盖服务端明确的等待要求，通常会让限流更严重。

要区分限流类型：input TPM 超限要缩小上下文，RPM 超限要降低请求数——两者的处置方向不同，退避只是争取时间，不解决根因。

信号与判定

观测信号判定含义
HTTP 429 且带 retry-after完全服从服务端节奏，本地序列不参与
HTTP 503 / 529 上游过载退避并把 cap 放宽到 120 秒，同时降低并发
连接超时或连接被重置退避重试；连续 3 次则触发端点轮换
同一步骤反复退避仍不推进判定为非瞬时故障，升级为熔断或换端点
退避次数到达上限停止自动重试，转入明确的终态：告警 + 留档

触发与处置

  1. 先判断可重试性：只对幂等且未产生副作用的步骤自动重试，写文件、提交、对外发消息必须先查状态再决定是否重放。
  2. 读取响应头里的 retry-after；没有该头再退回本地退避序列，避免用猜测覆盖服务端的要求。
  3. 计算等待时长：min(base × 2ⁿ, cap) 再乘抖动系数，保证多 worker 不会在同一秒集体重试。
  4. 重试期间降低并发并观察两个窗口，恢复时用加性增、失败时用乘性减，不要一次性恢复满速。
  5. 每次退避都写入干预存档：触发原因、等待时长、第几次重试，让报告能区分"任务慢"和"被限流"。
  6. 次数或时长到达上限即熔断，交由供应商轮换或终态报告处理，不允许无限期等待。

失效模式

固定间隔重试：每个 worker 都在同一个周期醒来，限流解除的瞬间被自己重新打满。

退避无上限：等待时间指数增长却永远不结束，任务卡在既非成功也非失败的中间态。

缺少抖动：多 worker 节奏一致，退避反而把重试对齐成尖峰。

对已产生副作用的工具调用盲目重放，造成重复写入、重复提交——退避救不了不幂等的操作。

判据： 退避的目标不是"再试一次"，而是让失败收敛成两种结局之一：恢复，或者明确地放弃。停在中间不算结果。
