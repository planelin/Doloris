# 第06章 上下文超长污染

## 症状

两种形态。硬失败：400 `context_length_exceeded` / prompt too long，请求直接被拒。软退化更常见也更贵——上下文没爆但已被垃圾填满：整份文件内容、几千行构建日志、失败工具的完整 stderr、同一段代码的多个历史版本都还留在会话里。表现为 agent 越跑越"傻"：重复已被否决的方案、引用早期错误结论、把已修好的报错当成现状、遗忘最新指令；同时每轮 input token 单调上升，延迟和成本一起涨。

## 处置

1. 先看曲线：把每轮 input token 打点，确认是"单调增长"（累积污染）还是"单点过大"（某次塞进了巨型文件）。
2. 立即截断工具输出：单条工具结果设上限（如 4KB / 200 行），超出只留头尾并标注 `...truncated N lines...`。
3. 压缩历史：把已完成阶段替换为一句结论 + 产物路径，删掉中间过程原文；错误日志只保留错误行，不留全量堆栈。
4. 硬失败时不要盲目重试同一请求（必然再失败），必须先缩上下文。
5. 最有效的兜底：**换会话续跑**——把状态写进 `PROGRESS.md` 一类的进度文件，起一个干净上下文，只读进度文件继续。

## 预防

把进度文件（而不是对话历史）当作唯一状态真值源，让"重启即恢复"成为常态而非救火手段。给每轮设 token 预算并在超阈值时自动摘要。用 grep/glob 定位后只读必要行，别整文件灌入。长任务切成小节，每节产出一个文件、勾一个 checklist、然后主动收缩上下文——分章写作这类任务天然适合这种切分。
