# 第11章 文件系统冲突与半成品写入

## 症状

产物"看起来有"但不可用：文件被截在半句话、JSON/YAML 缺尾括号、两个 worker 同写一个文件互相覆盖（后写者赢，前者的工作凭空消失）、编辑基于已过期的内容导致把别人的修改抹掉。Windows 上还多一类：文件被占用导致写入/改名失败（`Access is denied`、`file in use`），以及 CRLF/编码与路径大小写差异引发的"同名不同文件"。最隐蔽的是崩溃留下的半成品——大小非零、校验不做就发现不了，下游把它当完整输入继续跑。

## 处置

1. 先扫产物完整性：逐个检查大小、行数、结尾是否合法（Markdown 检查末尾小节、JSON 做一次解析），列出可疑清单，别只看文件是否存在。
2. 半成品一律隔离到 `*.partial` 或 `quarantine/`，绝不留在正式路径上；重写该项而不是修补字节。
3. 冲突文件用版本对比恢复：优先取仓库/备份中的版本，再把丢失的改动重放一遍。
4. 清理残留锁文件与临时文件（崩溃后遗留的 `.lock`、`.tmp`），否则重启会一直报"已被占用"。
5. 写入失败时区分权限、占用、路径不存在三种错误，处置完全不同。

## 预防

统一走原子写：写 `tmp` → flush/fsync → 校验 → 原子改名到目标；这样中断只会留下临时文件，正式产物永远完整。给每个 worker 划分独立目录或独立文件所有权，同一文件只允许一个写者；必须共享时用锁文件加超时。修改前先读、比对内容哈希，不匹配就放弃本次编辑而不是强写。跨平台项目固定 UTF-8（不带 BOM）与换行策略，避免大小写路径重名。关键节点做一次提交或快照，让"回到上一个已知良好状态"随时可用。
