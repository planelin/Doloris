# 第10章 进程僵死与心跳丢失

## 症状

进程还在（PID 存在），但不再产生任何输出：CPU 接近 0%、日志停在某一行、心跳文件时间戳不再更新。常见根因：等待 stdin 的交互式命令（分页器、确认提示、`git rebase -i`）、死锁或锁等待、半开 socket 上的无限读、子进程未回收导致的管道缓冲写满（stdout 缓冲区满后写方阻塞）、以及内存压力下的长时间换页。反面失效同样危险：看门狗阈值过短，把正在做长推理或长下载的健康进程反复误杀，看起来像"任务永远重启"。

## 处置

1. 先分类再动手：CPU 0% + 无 IO ≈ 真僵死；CPU 高但无输出 ≈ 死循环（见 ch07）；有 IO 无进展 ≈ 依赖慢（见 ch09）。
2. 杀之前先取证：抓栈（`jstack`/`py-spy`/`gdb`）、记录打开的文件与连接、保存最后 200 行日志和心跳时间戳，写成 crash 事件。否则重启后线索全丢。
3. 优雅→强制两段式终止：先发终止信号留出清理窗口（让它落盘断点），超时未退再强杀。
4. 从进度文件 resume，而不是从头重跑；重启前清理孤儿子进程与残留锁文件。
5. 记录重启计数，同一阶段连续重启 ≥3 次就停止自动恢复并告警——反复重启只会放大损失。

## 预防

心跳要带信息量：时间戳 + 当前阶段 + 已完成项数，这样"活着但空转"也能被发现。阈值分级：warn（如 90s）只告警，kill（如 300s）才动手，长推理阶段用更宽的阈值，避免误杀。看门狗必须与被监控进程分离（独立进程/独立机器），自己不能被同一个故障带走。所有命令强制非交互（`--yes`、`--no-pager`、`GIT_TERMINAL_PROMPT=0`），stdin 接 `/dev/null`；持续读走子进程 stdout/stderr 防止管道憋死；长连接开启 TCP keepalive。定期做混沌演练——随机 kill 一个 worker，验证心跳告警、断点续跑、重启上限三条链路真的生效。
