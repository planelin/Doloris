# 第05章 认证与key失效

## 症状

返回 401 `authentication_error`（`invalid x-api-key`）或 403 `permission_error`。特征是**所有**请求瞬间同时失败、成功率直接掉到 0 且不随时间恢复，与 429/5xx 的成片抖动不同。常见根因：key 被轮换或吊销、环境变量没加载到子进程（父 shell 有、worker 没有）、值里带了尾随换行/空格/BOM、写错了请求头名、用了错误的 base_url 与 key 组合、或代理层把 Authorization 头剥掉了。半夜跑的长任务遇到"到期轮换"是经典事故。

## 处置

1. 归为**不可重试** fatal：立刻停止该 key 的重试，别让退避逻辑刷 401 刷一整夜。
2. 打指纹自查：日志只记 key 的前 4 后 4 位加长度（如 `sk-a...9f2c len=108`），一眼就能看出是"没读到"（长度 0）还是"读错了"（长度不符/带空白）。绝不整值落盘。
3. 用最小探针请求单独验证 key，绕过代理再验一次，区分"key 无效"与"代理剥头"。
4. provider 池中标 `dead` 并轮转到备用 key；全池失效就保存断点、告警、停机等人。
5. 确认权限范围：403 往往不是 key 错，而是该 key 无权访问目标模型或功能。

## 预防

启动时做一次认证探活（发一个 1 token 的请求确认 200），把配置错挡在长任务之前。key 从密钥管理/环境注入，不进仓库、不进命令行参数（会落进进程列表和 shell 历史）。读取时统一 `strip()`，并校验前缀与长度。为 key 记录到期/轮换日期并提前提醒；池里始终保留一个已验证的备用 key。所有日志与报错输出走脱敏过滤器，避免把凭据写进 crash dump 或发给外部服务。
