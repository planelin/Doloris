# 第02章 上游5xx与网关错误

## 症状

返回 500/502/503/504，或收到 HTML 错误页而非 JSON（说明请求死在网关/代理层，没到模型服务）。`overloaded_error`（529）表示上游过载。特征是错误成片出现、跨多个 worker 同时发生，且与本地请求内容无关；重放同一请求有时成功有时失败。若挂了系统代理或反向代理做出口注入，网关自身的 502 会伪装成"模型故障"，容易误判。

## 处置

1. 先分层定位：直连一次最小请求（单条 ping/PONG 探针）。若直连成功而经代理失败，故障在代理层，不要去调模型参数。
2. 5xx 与 429 用同一套退避，但 503/529 的 `cap` 放宽到 120s，并降低并发。
3. 只对幂等步骤自动重试；已产生副作用的工具调用（写文件、提交、发消息）必须先查状态再决定是否重放，避免重复执行。
4. 解析响应前先看 `content-type`，非 JSON 直接归类为网关错误并原样存档，别让 JSON 解析异常掩盖真实错误码。
5. 连续 N 次（建议 3 次）5xx 就触发 provider 轮转或熔断，转到备用端点。

## 预防

给客户端配熔断器：滑动窗口内错误率超阈值就短路，半开状态用探针试探恢复。启动阶段做一次 provider 探活（发一个极小请求确认返回可解析），把"配置错/代理挂了"挡在长任务开始之前。所有 5xx 响应保留状态码、request-id、耗时和响应头快照，便于向上游报障。不要在代理层做静默重写，出口链路上的每一跳都要能在日志里被单独识别。
