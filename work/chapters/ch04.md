# 第04章 配额/余额耗尽

## 症状

返回 400/403 且错误类型为 `credit balance is too low`、`quota exceeded`、`billing`，或组织级月度上限用尽。与 429 的关键区别：429 等一会儿会恢复，配额耗尽等下去永远不会恢复——所以最典型的事故形态是"退避重试跑一整夜"，把有限的重试预算全烧在必然失败的请求上，还顺带刷出海量日志。多 key 池的场景下常见"逐个 key 依次阵亡"，最后整池不可用。

## 处置

1. 把配额类错误归入**不可重试**（fatal）分类，立刻停止该 key 的所有重试，不进退避队列。
2. provider 池中把该 key 标记为 `dead`（而非 `cooldown`），不参与轮转；剩余可用 key 数为 0 时直接暂停任务并告警，而不是空转。
3. 保存断点：写出当前进度文件（如 checklist、已完成产物清单），确保充值后能原地续跑而不是从头重跑。
4. 通知渠道要走带外（IM/邮件），别只写日志——无人值守时没人看日志。

## 预防

按 key 记录累计消耗并设两级阈值：80% 告警、95% 只允许收尾不再接新任务。长任务开跑前做预算估算（预计轮数 × 平均 token × 单价），估算超出剩余额度就拒绝启动。把"余额/配额剩余"做成主动探测的健康项而不是被动等报错。同时给单次运行加硬上限（最大轮数、最大 token、最大墙钟时间），防止逻辑循环把额度烧干。
