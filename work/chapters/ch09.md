# 第09章 依赖服务超时

## 症状

agent 本身没问题，卡在外部依赖上：MCP server 不响应、数据库连接池耗尽、内网 API 无返回、`git fetch` 卡在网络、DNS 解析挂住、镜像源拉不动。最典型的是**没设超时**——连接进入半开状态，TCP 层不报错，调用方无限等待，于是整条流程静默停摆几个小时。次典型是"超时设了但太长"：单步 600s，串起来三步就把整个运行窗口吃完。级联形态是一个慢依赖把线程池占满，导致本来健康的调用也开始排队超时。

## 处置

1. 分层定位：先判断是 DNS、TCP 连接、TLS 握手还是首字节等待慢，四者处置完全不同。
2. 立刻加超时并快速失败：连接超时 5s、读超时按业务定（LLM 流式用 token 间隔超时），总预算独立于单步超时。
3. 依赖不可用时走降级路径而非硬等：跳过该步骤、标记 `skipped_dependency_down`、把受影响产物记入待补清单，让主流程继续跑完能跑的部分。
4. 只重试幂等调用，且带退避与次数上限；对写操作先查询状态再决定是否重放。
5. 熔断：错误率超阈值就短路该依赖，半开探针恢复，避免慢依赖拖垮全局。

## 预防

规则化"任何跨进程/跨网络调用必须有显式超时"，代码评审时把无超时的调用当缺陷。维护一份依赖清单，每项标注：超时值、重试策略、是否可降级、降级后的影响。给依赖做主动健康检查而不是等业务报错。限制对单一依赖的并发（信号量隔离），并把每个依赖的 P99 延迟与超时计数纳入心跳，让"卡在哪儿"在看板上一眼可见。
