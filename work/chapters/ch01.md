# 第01章 API限流(429)

## 症状

请求返回 HTTP 429，响应体多为 `rate_limit_error`，响应头带 `retry-after`。日志表现为一段时间内成功率骤降到 0，随后自行恢复；agent 侧看起来像"卡住不动"，输出停滞但进程仍活着。典型触发点是并发扇出过大、重试风暴、或长上下文导致的 input token 速率超限（TPM 先爆，RPM 还没到）。多个 worker 共享同一 key 时，一个 worker 的重试会把其他 worker 一起拖进限流。

## 处置

1. 优先读 `retry-after` 头，按其值休眠；没有该头再退避。
2. 指数退避 + 抖动：`sleep = min(base * 2^n, cap) * (0.5 + rand*0.5)`，`cap` 取 60s，最多重试 5 次。禁止固定间隔重试。
3. 立刻把全局并发降到 1/2，观察两个窗口再逐步恢复（加性增、乘性减）。
4. 若有 provider 池，把当前 key 标记为 `cooldown`，轮转到下一个 key/端点继续跑，冷却到期再放回。
5. 区分限流类型：input TPM 超限要缩小上下文，RPM 超限要降请求数，两者处置方向不同。

## 预防

在客户端就放限速器（令牌桶），把速率压在配额的 80%，不要靠服务端 429 来做流控。为每个 key 记录 RPM/TPM 用量并暴露成指标；对长任务用队列串行化，避免瞬时扇出。把 429 计数、退避总时长、轮转次数写进心跳，让看板能区分"任务慢"和"被限流"。压测时验证退避逻辑真的会收敛，而不是把 5 个 worker 的重试对齐到同一秒。
