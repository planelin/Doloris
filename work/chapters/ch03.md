# 第03章 流式响应中断

## 症状

SSE 流开始正常吐字，中途断开：连接被 RST、读超时、或收到不完整的 JSON 分片而没有终止事件。表现为输出被截在半句话、工具调用参数只有前半段、`stop_reason` 缺失。最危险的变体是"静默截断"——流正常关闭但内容不完整，程序当成完整回复继续往下走，于是把半个 JSON 当作工具参数去执行。长时间无 token 产出（模型在做长推理）也会被中间设备当作空闲连接掐掉。

## 处置

1. 判定完成必须依据显式终止事件（`message_stop` / `stop_reason` 非空），不能依据"流关闭了"。缺终止事件即视为失败。
2. 校验累积内容：工具调用参数先做 JSON 完整性解析，解析失败就丢弃整轮，绝不半段执行。
3. 设"两次 token 之间"的空闲超时（如 60s），而不是整体请求超时，避免长输出被误杀。
4. 重试整轮请求，不要试图"续写"；已落盘的部分输出移到 `.partial` 文件，不覆盖正式产物。
5. 若可拿到 `usage`，比对已收 token 与预期，把截断事件单独计数上报。

## 预防

一律用流式而非阻塞式调用，好处是能靠 token 间隔判活；同时把 keepalive/心跳事件透传出来，别在中间层过滤掉。检查代理和负载均衡的 `proxy_read_timeout`、缓冲设置——开启响应缓冲会让 SSE 变成"憋到最后一次性返回"，直接破坏流式语义。写入产物遵循"先写临时文件、校验通过再原子改名"，让中断天然不产生半成品。
