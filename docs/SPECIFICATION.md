# AFK 长任务托管系统：设计准则与技术规范

> 审查、修改或重构本系统的维护者与 Agent 请先阅读本文。本文记录系统架构原则与目标行为规范；操作说明见 [USAGE.md](../USAGE.md)。

## 系统为什么存在

用户正在 Codex / Claude 等 Coding Agent 中执行一项耗时很长的任务，临时有事需要离开，于是启动 AFK 接管。用户回来时，期望至少有一项任务已经真正完成，而不是发现系统停在某轮选择题、确认问题或可以简单修复的报错上。

AFK 的核心价值是让任务在用户缺席时继续推进并完成。检测到停顿、保存状态、给出通知，都只是辅助能力，不能代替完成任务。

## AFK（kill / resume）的交接语义

- `afk.cmd` 启动并选定会话后，必须自动检查安全退出边界、退出 Codex App、确认写入权释放，再无头 resume **原会话**。不得将“等待用户关闭 App”作为必经步骤，`--yes` / 非交互也不能例外。
- 文件静默不等于模型空闲，更不等于写锁释放。不能用“rollout 修改时间连续 15 秒不变”授权接管，也不能在静默超时后强行并发 resume。
- 安全检查依据结构化生命周期和按 `call_id` 配对的工具事件；尚未返回的工具调用、损坏/不可读取的轨迹不能视为安全。模型侧可中断边界需要自动暂停并确认，再关闭 App；已终止的回合无需额外暂停。
- 关闭后必须复查桌面进程退出并检查原会话写锁；不能通过删除活跃锁文件绕过单写者保护。失败应保存状态、报告及通知，不盲杀、不假称接管成功。
- kill 会关闭整个 Codex 桌面端，不是只隐藏窗口。不要同时在该 App 中运行不希望被中断的其他任务；要保留 App 使用 AFK2。

## AFK2 的交接与续跑语义

- AFK2 是 **fork 无头续跑**，不是等待父任务自然完成，也不是让父子任务并行工作。
- 转无头前必须暂停并确认原任务停止；保留 Codex App 和父任务记录，但不让两边同时执行、重复消耗 token。暂停失败不能启动 fork。
- 启动时先取得工作区监管互斥锁并持久化 `HANDOFF_WAIT`，再发暂停请求；重复启动不得影响已有托管。取消或交接失败必须落盘终态、报告并释放本实例持有的锁。
- AFK2 的暂停确认等待**不设时限**，取消固定缓冲/超时：仍会自动请求暂停，但必须等到轨迹确认原回合停止才 fork。GUI 暂停回执、文件静默或等待时长都不能代替确认；已停止的父任务不必额外等待。等待期间可用 Ctrl+C 取消，不能因超时而强行并发。
- 切换带来的中断是必要交接；向 fork 子任务发送「继续」是合理的恢复指令，不应作为“错误注入”一律禁止。父任务已空闲时，不必再人为制造一次中断。
- 只有确实停在待决策问题时才先调用 L2；L2 明确批准的「继续」也应正常执行。无效/失败的 L2 决策不能用「继续」绕过。
- “减少不必要的打断”应约束运行中的额外干预，不能删除 AFK2 交接所必需的暂停和续跑机制。

## AFK3 的 GUI 身份与送达语义

- `afk3.cmd` 保留 Worker 在 Codex App 中执行，由 L2 通过 GUI 交还指令；不关闭 App，也不 fork Worker。
- 暂停/发送必须证明活动任务的精确 SID，并将输入框和按钮搜索限定在已验证的任务面板。相同标题、侧栏可见或被选中、正文中提到 SID 都不能证明目标身份；无法验证时不输入、不暂停其他任务。
- `NOT_SENT` 才允许有界重试；`SENT` / `UNCERTAIN` 必须先核对目标轨迹中的新指令接收事件，不能盲重发。mtime、token 统计和不相关消息都不是 ACK。
- 轨迹缺失、损坏或未完整落盘时为 unknown，不等于空闲；已中断回合不得重新激活更早的提问。
- GUI 与无头模式共用无人值守决策、修复及证据验收原则，不得退回旧式常规等待人工路径。

## 托管期间的决策归属

- L1 编排器负责观察、分派、执行、重试和记录；L2 AGY 负责判断、决策、修复取舍和验收。
- 人工回复不应成为托管流程中的必经环节。不能把 `WAITING_USER`、`request_user` 或 `DEFER` 当作常规决策问题的最终归宿，然后退出并等待不在场的用户。
- Worker 原本向用户提出的问题，应交给 L2 AGY 根据任务目标和已有上下文作出决定，再将具体指令交还 Worker 推进任务。
- “向用户确认主视觉方向，再继续”这类确认节点，在托管状态下应进入 L2 决策流程；不能仅凭“向用户确认”几个字就在本地拦截，禁止 L2 代答。
- 启动托管意味着把任务内的常规决策交给 L2；不意味着可以任意扩大任务范围、绕过真实权限限制或伪造用户授权。遇到这类约束也应交给 L2 判断可行替代方案或有依据的停止理由，不能设计成必须等待人工回复才能走完的流程。

## 报错和修复

- 可以简单修复的本地、环境或执行错误，应进入 L2 诊断与修复流程，修复后验证并继续任务。
- 上游服务器崩溃、限额用尽等难以修复的错误，不要求强行修复，也不要求无休止重试。
- 是否不修复、是否还有替代方案、是否应该结束本轮托管，决策权仍在 L2 AGY。L1 不能仅凭一个错误分类或本地关键词规则替 L2 作出放弃决定。
- 若 L2 通道本身不可用，应保留证据并进行有界恢复；最终仍不可用时如实记录基础设施失败，不能伪称 L2 已决定放弃，也不能伪装成等待人工决策。

## 什么才算完成或合理停止

- 正常终点是原任务有真实交付，且通过基于证据的验收。不能用补完成措辞、勾选清单、刷新文件时间等方式制造成功信号。
- 一次提问、一个可修复错误、一次 Worker 回合结束，都不是任务完成，也不应自动成为托管结束的理由。
- 无法继续时，应记录 L2 的判断、阻塞证据、已尝试措施及未完成内容；真实基础设施故障应明确区分。完成目标不能变成对所有故障都承诺成功。
- 每条退出路径都应保存一致的最终状态和报告，并执行已配置的通知。通知用于让用户回来后了解结果，不是请求用户即时回复后才能继续。

## 源码审查与修改的检查标准

1. 决策问题是否真正到达 L2，还是被 L1 提前转人工、提前退出？
2. L2 的决定是否落实为 Worker 后续执行，而不只是记入日志？
3. 简单故障是否经过诊断、修复、验证并恢复执行？难修复故障的放弃判断是否有 L2 依据？
4. 状态机是否存在必须等人工回复才能继续的常规路径？如有，应按本产品目标重新设计。
5. 所谓“安全改进”是否把系统改成了一个遇到问题就停的提醒器，削弱了无人值守完成任务的能力？
6. 测试是否验证了“提问 → L2 决策 → Worker 继续 → 实际验收”以及“报错 → L2 修复取舍 → 恢复或有依据地停止”的完整链路？仅断言进入 `WAITING_USER` 不能证明托管成功。
